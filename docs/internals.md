# 内部机制与兼容性

本文面向需要排查兼容问题或修改实现的维护者。这里记录的是当前实现依据和行为边界，不是 Claude Code 的公开契约；普通使用从 [README](../README.md) 开始

## 版本证据与验证口径

cron-up 依赖的上游机制没有稳定性承诺，不能把“2.1 以上”视为完整的兼容声明。当前仓库中已有的核对记录如下：

| 机制 | 已有核对依据 | 使用时的含义 |
| --- | --- | --- |
| 7 天周期任务回收与任务归属字段 | Claude Code 2.1.300 起有核对记录 | 更早版本不能据此推断可用 |
| 逐任务调度谓词与目录级调度锁 | Claude Code 2.1.302 二进制 | 一任务一会话的核心依据 |
| Herdr 原生启动、标签、`hc kill` 与历史读取 | Herdr Core 0.1.18，本机隔离任务实测 | 所有新预热会话的唯一后端；其他版本未验证 |
| Claude Code `--name` 会话与终端标题 | Claude Code 2.1.319、Herdr Core 0.1.18，本机隔离启动实测 | 只证明该版本组合的名称上报链路，不扩大其他核心行为的兼容基线 |
| 锚点启动后的 OSC 0 标题 | Herdr Core 0.1.18，本机隔离 zsh，启动后发送 `printf` 实测 | 已核对 Core 标题更新及后续交互命令后的保留；App 是否展示不在此保证范围内 |
| 任务文件与 `~/.claude/sessions/` 会话登记 | 当前实现以 2.1.302 为本机核对基线 | 登记格式漂移时只能提供烟雾告警，不能证明所有语义仍兼容 |
| 投递抖动默认值与算法 | Claude Code 2.1.285，darwin-arm64，2026-09-30 安装的二进制 | 不能写成已经在 2.1.302 重新验证；远程配置还可能覆盖默认值 |

这张表记录已有证据，不是“只有列出的版本才能运行”的断言。低于或高于核心基线的版本都按未验证处理；升级后应：

1. 运行 `cron-up`，查看会话登记、启动链和预热告警
2. 用低风险任务验证发现、预热、投递和回收的完整链路
3. 若预计投递与实际投递持续出现系统性偏差，重新核对上游算法，而不是只调整本地显示常量

`src/constants.mjs` 中的 `CC_JITTER` 注释还记录了上游远程配置键 `tengu_kairos_cron_config`。运行时的远程配置可能改变投递行为，因此本地逆向常量只能用于估算

## 工作区与任务身份

- 工作区是包含 `.claude/scheduled_tasks.json` 的精确目录，不自动等同于 Git 根目录
- 扫描从 roots 开始，root 本身及其下第 1 至第 3 层都检查候选文件；符号链接形式的子目录不递归，排除名单由 `PRUNE_DIRS` 定义
- 原生任务优先使用唯一 `id` 作为状态键；缺少 id 的手写任务使用稳定内容摘要形成 `anon:` 键
- 同一个状态键对应多条任务时，无法唯一映射会话，巡检跳过这些条目的预热与归属改写并给出告警
- 推荐入口是 Claude Code 的 CronCreate（`durable: true`）；手写或第三方生成文件只是兼容性用法，字段必须遵循上游语义

### 工作区模型配置

- `<工作区>/.claude/cron-up.json` 是 cron-up 自己读取的可选配置，不属于 Claude Code 任务文件格式；任务级 `tasks.<任务键>.model` 覆盖顶层 `model`
- 有可用模型时，启动命令追加 `--model <值>`；没有配置时完全不传该参数，不改变 Claude Code 的默认选择
- 配置存在但不可解读或字段形状不对时，该工作区冻结新启动，保留已有会话管理，也不累计启动失败；这样不会把配置错误静默降级成默认模型
- 模型是每次启动的输入，不写入 state，也不对活会话做热切换。`list` 展示当前配置而非实际启动快照；高频任务长期复用会话时，修改配置可能要到后续重新预热才生效
- 原创建者会话在线时仍走原有的不预热分支，工作区模型配置不会替换那个会话的模型

## 逐任务归属与调度谓词

Claude Code 2.1.302 中核对到的投递判定按以下优先级理解：

1. 任务没有归属会话：只有持目录调度锁的会话投递
2. 任务归属当前会话：当前会话投递，不需要目录锁
3. 当前进程是任务记录的创建者进程（resume 形态）：可以投递
4. 其他情况：会话必须持锁、任务属于本项目，并且记录中的创建者进程已死，才可接管

cron-up 为进入窗口且原归属不在场的任务分别启动会话，认亲后把任务归属写到对应 sessionId 和进程指纹。这样，同目录同时到期的不同任务不必共享一个交互会话

“原创建者在线时不碰任务”只适用于**不预热、不改写归属**；自动续期与周期任务 ID 改小仍会修改显式周期任务

某个预热中途退出后，其他符合上游规则的活会话仍可能按第 4 条接管，但这不是 cron-up 对执行结果的额外保证

## 巡检与会话生命周期

主要常量集中在 [`src/constants.mjs`](../src/constants.mjs)，数值以源码为准；本文解释其语义和派生关系。修改常量时应同时核对状态机，而不是只改文档

| 常量 | 含义 |
| --- | --- |
| `INTERVAL_SECONDS` | launchd 相邻巡检轮次的目标间隔，休眠时可能漏轮 |
| `LEAD_SECONDS` | 周期任务的预热前瞻量 |
| `MAX_SCAN_DEPTH` | root 下最多再下降的层数，最大深度本身仍检查任务文件 |
| `WARMUP_POLL_MS` | 新会话启动后，当轮重扫会话登记的间隔 |
| `WARMUP_WAIT_MS` | 当轮等待认亲的上限，不是判死时限 |
| `WARMUP_GRACE_SECONDS` | 未登记进程超过该年龄后，才在跨轮状态机中判卡死 |
| `FAIL_LIMIT` | 没有成功登记的启动失败达到该次数后进入冷却 |
| `COOLDOWN_SECONDS` | 单任务暂停重试的时间 |
| `FAIL_TTL_SECONDS` | 已死亡条目的失败记录跨预热窗口保留后的老化时限；活条目和冷却条目按各自状态保留 |
| `SESSION_RECYCLE_IDLE_SECONDS` | 下一代预热替换上一代前，要求界面静默的时长；不是执行后的回收倒计时 |
| `HEARTBEAT_STALE_FACTOR` | 心跳超过该倍数的巡检间隔未更新时提示沉默 |
| `PATROL_LOG_ROTATE_BYTES` | 单个巡检日志超过该大小后，在轮初轮转 |
| `DISPLAY_SEARCH_DAYS` | `list` 和总览寻找未来落点的展示窗口 |
| `AUTO_MIN_ID_TARGET_DELAY_MS` | 判断现有周期任务 ID 是否可保留的延迟目标；按尾窗覆盖的最长周期间隔反解阈值，需要改号时实际从 `00000001` 起分配空号 |

一次性任务的预热前瞻统一额外增加 `CC_JITTER.oneShotMaxMs`，窗口前沿为 `落点 - LEAD_SECONDS - CC_JITTER.oneShotMaxMs`。**所有一次性任务都使用该保守窗口**，不是只有 `:00`／`:30` 网格任务；额外前瞻用于覆盖网格任务可能提前投递的相位，非网格任务也采用同一口径。实际启动仍取决于巡检相位和运行状态

### 一轮巡检的主要阶段

1. 获取巡检互斥锁，读取配置、状态、心跳和 Claude Code 会话登记
2. 发现工作区，按任务逐组处理；单个工作区出错不应阻断后续工作区
3. 已有条目先尝试认亲，成功后回填 sessionId、Claude pid 和进程启动指纹，并清零失败计数
4. 依次处理原创建者在线、终端 resume 接管、下一代预热前换代、预热窗口、卡死退休、冷却和重新启动
5. 合并自动续期、周期任务 ID 改小与归属改写，同步迁移 state、pending 和 Herdr 标签；新启动的会话在当轮等待认亲后再尝试补写归属
6. 回收任务已经删除的会话，保存仍有效的状态和本轮心跳

### 启动失败与卡死不是同一计时器

- `WARMUP_WAIT_MS` 的当轮等待结束只会停止等待，不增加失败计数，也不直接杀死仍存活的进程
- 未登记进程年龄超过 `WARMUP_GRACE_SECONDS` 后，由后续巡检执行卡死退休，而不是由到达阈值就精确触发的独立定时器处置
- 启动即失败、启动后死亡和卡死退休都会进入失败流程；成功认亲会清零失败计数
- 已死亡条目的失败记录按任务保留，可跨稀疏任务的多个预热窗口累计，并按 `FAIL_TTL_SECONDS` 老化；因此 `FAIL_LIMIT` 统计的不是“连续若干个巡检轮次”

### 下一代预热时替换上一代

周期任务在本代投递后保留会话，不按固定静默时长提前回收。设本代 `lastFiredAt` 之后的下一个 cron 落点为 `nextSlot`，则下一代预热起点为 `nextSlot - LEAD_SECONDS`。到达这个起点后，替换还需要同时满足：

- `lastFiredAt` 表明该任务在本代会话启动后已经触发
- 当前时间已经不早于上述下一代预热起点，且该起点晚于本代 `lastFiredAt`
- Herdr 界面静默超过 `SESSION_RECYCLE_IDLE_SECONDS`

满足后，同一轮先结束上一代，再启动下一代并按既有等待流程登记、盖印，不能只停旧后等下一轮才启动。仍有界面输出时暂不替换；如果上次投递前就已经进入下次预热，说明高频相邻执行之间没有独立换代间隙，继续复用现有会话

只有已经满足其他换代条件、真正需要判断界面是否静默时，巡检才读取 Herdr 状态与可见界面，平静轮不做这项查询。状态为 `working` 时始终视为活跃，否则用界面内容摘要是否变化更新活动时间；首次查询只建立摘要基线，缺少终端地址或读取失败时也把活动时间推后，证据不足就不强行换代

这些条件只说明“可以按当前模型换代”，不证明 prompt 的所有副作用都已成功完成。等待人工回答的会话也会保留到下一代预热，再按同一规则替换；`lastFiredAt` 只参与代次判断，不是成功事件，也不再为它额外保存观测状态

任务被删除或一次性任务执行后从文件中消失时，还会走对应的条目清理路径

若工作区整个离开扫描视野，巡检无法继续按该任务状态做回收；总览会尽量报告仍能识别的运行中会话

## 任务文件维护与并发

每轮维护分三类：

- **续期**：只要 `recurring` 为真且 `permanent` 尚未为真，就写入 `permanent: true`，不依赖任务是否进入预热窗口
- **周期任务 ID 改小**：把显式周期任务的大 ID 或非原生 ID 改成 `00000001` 起的空号，消除按 ID 计算的投递偏移。空号分配同时排除任务文件、现存 state 和模型配置里的 ID，避免继承已删除任务的会话或模型。一次性任务不碰，已达标的小号不重排，第二轮保持字节级不动；原始任务键重复的组无法唯一映射，跳过改号
- **归属改写**：只针对进入窗口且需要预热的唯一任务键，写入 `createdBySessionId`、`createdByPid`、`createdByProcStart`

改号与归属改写是两项独立维护：归属改写本身不针对 `prompt`、`cron`、`createdInProject`，内容相同但 ID 不同的任务分别定位；重复 ID 或重复匿名键无法唯一映射时跳过

改号成功后，同一轮迁移 state 键与 pending 键，并同步 Herdr 的 `cron-up=<任务键>` 标签。state 额外保存稳定内容签名 `sig`，用于认回「任务文件已改号、state 尚未落盘」的崩溃窗口；`herdrTaskId` 只在终端标签仍落后于 `taskId` 时保存，标签同步失败时按旧标签做停止前身份核验，确认一致后删除该字段并在后续读取时回退到 `taskId`。已经运行的 Claude 调度器可能仍持有旧 ID，新 ID 最迟在下一代会话启动后生效

任务级模型配置使用同一任务键。改号前先把旧键值复制到新键并保留旧键，再写任务文件，避免跨文件切换期间丢失模型覆盖；配置无法解读时暂缓改号，续期与已有会话管理不受这一暂缓影响

同一批续期、周期任务 ID 改小和已有条目的归属改写会合并写入；模型配置别名如需新增，会在任务文件之前单独原子写入。新启动的会话在等待期认亲后，可能通过补盖流程另做一次归属写入；补盖不再改号，避免第二次写入绕开同一轮的 state、pending 与 Herdr 标签迁移。这些路径都使用同目录临时文件和原子替换：

- 临时文件先以 0600 创建，再尽量保留原任务文件权限
- 读取与写入之间使用 `mtimeNs` 做乐观检测，检测到其他写者改动时放弃本轮写入
- 这不是跨进程 CAS，也不是与 Claude Code 共用的锁；最后检查之后、`rename` 之前仍有一个无法由 cron-up 单方面关闭的竞态窗口

因此，文档不能把原子替换表述为绝不覆盖并发更新，卸载也不会回滚已经完成的续期、ID 改小、模型配置别名或归属改写

## 投递时间算法

以下算法用于 `cron-up list`、总览的“最近”和预热尾窗估算。它是上游内部实现的复刻，不是 cron-up 自己决定的调度策略

### 任务 id 的归一化值

当前实现对原生十六进制任务 id 取前 8 位，解析后除以 `2^32`，得到 `[0, 1)` 范围内的固定值，记作 `h`。同一 id 每次计算相同，不是每次触发重新随机

手写非标准 id 的解析不应被当作稳定兼容接口；推荐让 CronCreate 生成 id

### 周期任务

对某个 cron 落点，先计算它到下一落点的实际间隔 `period`，再估算：

```text
delay = min(h × 0.5 × period, 30 分钟)
预计投递 = 本落点 + delay
```

每日任务周期较长，很多原生随机 id 会触及 30 分钟上限。落点已经过去、预计投递尚未到来时，仍属于需要会话在场的尾窗，不能按“下一次未来落点”提前回收

代码已记录但**没有复刻**一个上游例外：相邻落点间隔约在 `[300000, 315000)` ms、且表达式匹配上游内部步进规则时，存在 `cacheLeadMs` 提前 15 秒的分支，例如部分约 5 分钟周期任务。对这类任务：

- “周期任务一律在落点后投递”的说法不成立
- 当前 `list` 的预计时间可能与上游实际调度存在约 15 秒或更多的系统性差异
- 是否补齐该分支需要单独实现和测试，不能只改文档宣称已经支持

### 一次性任务

- 落点分钟不属于 `:00`／`:30` 网格时，当前估算不增加投递提前量
- 落点属于网格时，按 `h × 90 秒` 提前，且不早于当前时刻
- 无论是否属于网格，巡检的预热前瞻都统一额外增加 90 秒，原因见生命周期章节

会话内部还存在秒级轮询尾差，因此“预计投递时间”不等于对实际开始执行时刻的保证

### 展示边界

未来落点的展示搜索范围由 `DISPLAY_SEARCH_DAYS` 定义。“一年内无”既包括下一落点超出展示窗口的表达式，例如部分闰日任务，也包括字段可以解析、但日历上永远无法匹配的表达式，例如 `0 0 30 2 *`

“cron 无效”只用于表达式解析失败，或字段值域、区间导致合法值集合为空；它与“一年内无”不是同一状态

## 会话登记、认亲与接管

### Herdr 启动层

Herdr 是必需依赖。安装与巡检先检查 `PATH` 和 `~/.local/bin/hc`，找不到就明确失败；新会话统一使用 `hc run --json --bg --no-parent --cwd <工作区> --label cron-up=<任务键> --label herdr.space=cron-tasks`。`--no-parent` 让终端不归属发起方，也不随父终端退出，不设置 Herdr 终端的自定义 `name` 或使用 `--rm`

每轮巡检通过 `hc ls --json --label cron-up-anchor=1` 检查命名锚点，并对候选逐个执行 `hc get --json` 核对完整标签和根 pid。任一存活锚点存在就复用，不重复启动；确认缺失后才创建 `/tmp/cron-tasks`，执行 `hc run --json --bg --no-parent --cwd /tmp/cron-tasks --label cron-up-anchor=1 --label herdr.space=cron-tasks --label herdr.tab=cron-tasks-anchor /bin/zsh -il`。启动身份核验后，再通过 `hc send` 让新 zsh 执行一次 `printf '\033]0;%s\a' cron-tasks-anchor`，由 shell 输出 OSC 0，把 Core 的 `terminal.title` 设为锚点 ID。命名只在本轮新锚点上尝试一次，复用已有锚点不重发；发送失败附带 `titleError`，由巡检单独告警，不删除锚点、不记作启动失败，也不阻塞任务预热

锚点不启动 Claude，也不写入任务 state。列表或身份查询失败会告警并跳过本次锚点启动，不能把证据不足当成缺失而双开；锚点启动失败不阻塞任务预热，下轮重试

锚点用于尽力让 space 默认显示为 `cron-tasks`，不是名称或布局保证。cron-up 不修改已有显式名称，不查询或调整 tab 顺序；手动移位、关闭后补开未能回到第一位等情况导致名称变化，属于可接受的显示效果。可靠边界是固定归组、每轮检查锚点和避免重复启动。cron-up 只使用 `hc` 操作 Core，不调用 App 命令，也不通过 `hc connect` 读写 App 私有文档

`cron-up=<任务键>` 是任务机器身份，供孤儿认领和停止前身份核对；`cron-up-anchor=1` 是独立的锚点身份，不占用任务 id。任务终端不传 `herdr.tab`，锚点使用固定 tab id。任务 prompt 的首个非空行压缩为单行摘要后传给 `claude --name`，与 list、总览共用 `taskSummary`；Claude Code 负责会话命名和终端标题上报，cron-up 不额外生成 AI 摘要，也不设置 `where`。启动参数不追溯修改已运行会话。卸载通过全量 Herdr 清单同时停止任务终端与锚点，两者都核对根 pid、启动指纹、cwd 和各自机器标签。已有终端不会被批量换组，需要时用 `hc label <地址> herdr.space=cron-tasks` 手动补充

`hc` 使用 core 的登录会话环境，而不是调用方 `execFile` 的环境。启动命令直接执行 `/bin/zsh -lic <claude 命令>`，由 zsh 按正常规则加载登录与交互配置，让 `claude` 函数、路由和模型配置生效；不再叠加第二层 zsh、手工 `source ~/.zshrc`、清理 `CLAUDE_CODE_*` 或构造调用方环境。启动时传入任务摘要 `--name` 与显式配置的 `--model`，不传 `--permission-mode`，权限模式及其余行为遵循 Claude Code 自身配置

0.1.18 的 `hc run --json` 与 `hc ls --json` 都只返回摘要，完整根 pid、标签和状态仍需 `hc get --json`。启动取得地址后必须查询根 pid 和进程启动指纹；地址缺失、pid 无效或指纹读取失败时不写 state，已确认创建的终端会用 `hc kill` 清理。启动失败不再直拉第二个会话，后续巡检可按 `cron-up=<任务键>` 和工作区认领仍存活的终端；包括上次启动失败后留下的 `pid=null` 条目，也不能跳过认领。列表或身份查询失败、认领对象读不到启动指纹时，本轮跳过新启动，不能把证据不足当作没有孤儿

### 进程结构与认亲

新会话的典型结构为：

```text
Herdr Core holder
  └─ /bin/zsh -lic（state 根进程）
      └─ claude（会话登记记录这一层）
```

巡检沿 Claude 的 ppid 祖先链找到 state 根进程。0.1.18 实测 Herdr 根 zsh 与 Claude 属于不同进程组，因此停止前必须核对根进程启动指纹、终端地址、根 pid、工作区和任务标签，再用 `hc kill` 结束终端。`hc kill --json` 自己等待停止升级完成并返回最终 `state`，本地不再重复轮询。Herdr 不使用 `--rm`，退出后的界面历史仍可供 `hc read` 与 `cron-up logs` 读取

巡检读取 `~/.claude/sessions/*.json`，结合进程存活、cwd 和祖先链，把根进程与登记的 sessionId 对应起来。认亲扫描用一张全机 `ps` 快照同时取得 ppid 与 comm，避免为每个原生 Claude 再执行一次单 pid 查询；`list` 与总览不需要祖先链，会跳过这张快照。登记是上游输出，不是稳定 API；读取器包含三类烟雾告警：

- 有登记文件但识别不到 interactive 会话
- 存活登记进程都不是可识别的 `claude`
- interactive 会话缺少有效 pid 或工作目录

这些告警只能覆盖已知漂移形态，不能证明上游所有内部语义均未变化

其他恢复机制：

- **终端接管**：state 根进程已退出但同一 sessionId 仍在其他终端存活时，不再另拉或结束该会话
- **孤儿认领**：state 丢失时，按 Herdr 任务标签和工作区认领
- **停止保护**：Herdr 先核对根进程启动指纹和终端元数据，再调用 `hc kill`

## 日志与隐私

- 巡检日志位于 `~/Library/Logs/cron-up/launchd.{out,err}.log`，默认 `cron-up logs` 展示当前 stdout 日志最近 100 行
- 会话界面与历史统一由 Herdr 保存；`cron-up logs <片段>` 先尝试精确地址查询，未命中再按目录、任务 id 或标题模糊匹配。读取使用 `hc read`，`-f` 对活跃终端使用 `hc attach`
- Herdr 界面与历史的保存位置和权限由 Herdr 自己管理
- Claude Code 自己仍在 `~/.claude/projects/` 保存对话记录，cron-up 的 `--purge` 不删除这些记录
