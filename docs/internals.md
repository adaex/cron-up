# 内部机制与兼容性

本文面向需要排查兼容问题或修改实现的维护者。这里记录的是当前实现依据和行为边界，不是 Claude Code 的公开契约；普通使用从 [README](../README.md) 开始

## 版本证据与验证口径

cron-up 依赖的上游机制没有稳定性承诺，不能把“2.1 以上”视为完整的兼容声明。当前仓库中已有的核对记录如下：

| 机制 | 已有核对依据 | 使用时的含义 |
| --- | --- | --- |
| 7 天周期任务回收与任务归属字段 | Claude Code 2.1.300 起有核对记录 | 更早版本不能据此推断可用 |
| 逐任务调度谓词与目录级调度锁 | Claude Code 2.1.302 二进制 | 一任务一会话的核心依据 |
| `script → zsh → claude` 三代进程结构 | 本机 Claude Code 2.1.302 | 会话认亲和进程回收依赖这一结构及祖先链识别 |
| 任务文件与 `~/.claude/sessions/` 会话登记 | 当前实现以 2.1.302 为本机核对基线 | 登记格式漂移时只能提供烟雾告警，不能证明所有语义仍兼容 |
| 投递抖动默认值与算法 | Claude Code 2.1.285，darwin-arm64，2026-09-30 安装的二进制 | 不能写成已经在 2.1.302 重新验证；远程配置还可能覆盖默认值 |

这张表记录已有证据，不是“只有列出的版本才能运行”的断言。低于或高于核心基线的版本都按未验证处理；升级后应：

1. 运行 `cron-up`，查看会话登记、启动链和预热告警
2. 用低风险任务验证发现、预热、投递和回收的完整链路
3. 若预计投递与实际投递持续出现系统性偏差，重新核对上游算法，而不是只调整本地显示常量

`src/constants.mjs` 中的 `CC_JITTER` 注释还记录了上游远程配置键 `tengu_kairos_cron_config`。运行时的远程配置可能改变投递行为，因此本地逆向常量只能用于估算

## 工作区与任务身份

- 工作区是包含 `.claude/scheduled_tasks.json` 的精确目录，不自动等同于 Git 根目录
- 扫描从 roots 开始，root 本身及其下第 1 至第 3 层都检查候选文件；符号链接形式的子目录不递归，排除名单由 `PRUNE_DIRS` 定义
- 原生任务优先使用唯一 `id` 作为状态键；缺少 id 的手写任务使用稳定内容摘要形成 `anon:` 键
- 同一个状态键对应多条任务时，无法唯一映射会话，巡检跳过这些条目的预热与归属改写并给出告警
- 推荐入口是 Claude Code 的 CronCreate（`durable: true`）；手写或第三方生成文件只是兼容性用法，字段必须遵循上游语义

## 逐任务归属与调度谓词

Claude Code 2.1.302 中核对到的投递判定按以下优先级理解：

1. 任务没有归属会话：只有持目录调度锁的会话投递
2. 任务归属当前会话：当前会话投递，不需要目录锁
3. 当前进程是任务记录的创建者进程（resume 形态）：可以投递
4. 其他情况：会话必须持锁、任务属于本项目，并且记录中的创建者进程已死，才可接管

cron-up 为进入窗口且原归属不在场的任务分别启动会话，认亲后把任务归属写到对应 sessionId 和进程指纹。这样，同目录同时到期的不同任务不必共享一个交互会话

“原创建者在线时不碰任务”只适用于**不预热、不改写归属**；自动续期仍会修改显式周期任务的 `permanent` 字段

某个预热中途退出后，其他符合上游规则的活会话仍可能按第 4 条接管，但这不是 cron-up 对执行结果的额外保证

## 巡检与会话生命周期

主要常量集中在 [`src/constants.mjs`](../src/constants.mjs)，数值以源码为准；本文解释其语义和派生关系。修改常量时应同时核对状态机，而不是只改文档

| 常量 | 含义 |
| --- | --- |
| `INTERVAL_SECONDS` | launchd 相邻巡检轮次的目标间隔，休眠时可能漏轮 |
| `LEAD_SECONDS` | 周期任务的预热前瞻量 |
| `MAX_SCAN_DEPTH` | root 下最多再下降的层数，最大深度本身仍检查任务文件 |
| `WARMUP_POLL_MS` | 新会话启动后，当轮重扫会话登记的间隔 |
| `WARMUP_WAIT_MS` | 当轮等待认亲的上限，不是判死时限 |
| `WARMUP_GRACE_SECONDS` | 未登记进程超过该年龄后，才在跨轮状态机中判卡死 |
| `FAIL_LIMIT` | 没有成功登记的启动失败达到该次数后进入冷却 |
| `COOLDOWN_SECONDS` | 单任务暂停重试的时间 |
| `FAIL_TTL_SECONDS` | 已死亡条目的失败记录跨预热窗口保留后的老化时限；活条目和冷却条目按各自状态保留 |
| `SESSION_RECYCLE_IDLE_SECONDS` | 与 `WARMUP_GRACE_SECONDS` 同值；回收判断要求的界面静默时长 |
| `SESSION_FIRE_MARGIN_SECONDS` | 除一个巡检间隔外，为下次触发预留的余量 |
| `SESSION_RECYCLE_MARGIN_SECONDS` | 等于 `SESSION_FIRE_MARGIN_SECONDS + INTERVAL_SECONDS`；回收要求距下次需要超过该余量 |
| `HEARTBEAT_STALE_FACTOR` | 心跳超过该倍数的巡检间隔未更新时提示沉默 |
| `PATROL_LOG_ROTATE_BYTES` | 单个巡检日志超过该大小后，在轮初轮转 |
| `DISPLAY_SEARCH_DAYS` | `list` 和总览寻找未来落点的展示窗口 |

一次性任务的预热前瞻统一额外增加 `CC_JITTER.oneShotMaxMs`，窗口前沿为 `落点 - LEAD_SECONDS - CC_JITTER.oneShotMaxMs`。**所有一次性任务都使用该保守窗口**，不是只有 `:00`／`:30` 网格任务；额外前瞻用于覆盖网格任务可能提前投递的相位，非网格任务也采用同一口径。实际启动仍取决于巡检相位和运行状态

### 一轮巡检的主要阶段

1. 获取巡检互斥锁，读取配置、状态、心跳和 Claude Code 会话登记
2. 发现工作区，按任务逐组处理；单个工作区出错不应阻断后续工作区
3. 已有条目先尝试认亲，成功后回填 sessionId、Claude pid 和进程启动指纹，并清零失败计数
4. 依次处理原创建者在线、终端 resume 接管、执行后回收、预热窗口、卡死退休、冷却和重新启动
5. 合并自动续期与归属改写；新启动的会话在当轮等待认亲后再尝试补写归属
6. 回收任务已经删除的会话，保存仍有效的状态和本轮心跳

### 启动失败与卡死不是同一计时器

- `WARMUP_WAIT_MS` 的当轮等待结束只会停止等待，不增加失败计数，也不直接杀死仍存活的进程
- 未登记进程年龄超过 `WARMUP_GRACE_SECONDS` 后，由后续巡检执行卡死退休，而不是由到达阈值就精确触发的独立定时器处置
- 启动即失败、启动后死亡和卡死退休都会进入失败流程；成功认亲会清零失败计数
- 已死亡条目的失败记录按任务保留，可跨稀疏任务的多个预热窗口累计，并按 `FAIL_TTL_SECONDS` 老化；因此 `FAIL_LIMIT` 统计的不是“连续若干个巡检轮次”

### 回收是启发式判断

周期任务的会话回收需要同时满足：

- `lastFiredAt` 表明该任务在本代会话启动后已经触发
- 会话界面日志静默超过 `SESSION_RECYCLE_IDLE_SECONDS`
- 距该任务下次需要会话超过 `SESSION_RECYCLE_MARGIN_SECONDS`

这些条件只说明“可以按当前模型回收”，不证明 prompt 的所有副作用都已成功完成。任一条件不满足时会继续复用现有会话；高频周期任务可能因始终不满足回收余量而长期复用同一会话

任务被删除或一次性任务执行后从文件中消失时，还会走对应的条目清理路径

若工作区整个离开扫描视野，巡检无法继续按该任务状态做回收；总览会尽量报告仍能识别的运行中会话

## 任务文件维护与并发

每轮维护分两类：

- **续期**：只要 `recurring` 为真且 `permanent` 尚未为真，就写入 `permanent: true`，不依赖任务是否进入预热窗口
- **归属改写**：只针对进入窗口且需要预热的唯一任务键，写入 `createdBySessionId`、`createdByPid`、`createdByProcStart`

归属改写不以修改 `prompt`、`cron`、`id`、`createdInProject` 为目标。内容相同但 id 不同的任务分别定位；重复 id 或重复匿名键无法唯一映射时跳过

同一批续期和已有条目的归属改写会合并写入；本轮新启动的会话在等待期认亲后，可能通过补盖流程另做一次归属写入。两条路径都使用同目录临时文件和原子替换：

- 临时文件先以 0600 创建，再尽量保留原任务文件权限
- 读取与写入之间使用 `mtimeNs` 做乐观检测，检测到其他写者改动时放弃本轮写入
- 这不是跨进程 CAS，也不是与 Claude Code 共用的锁；最后检查之后、`rename` 之前仍有一个无法由 cron-up 单方面关闭的竞态窗口

因此，文档不能把原子替换表述为绝不覆盖并发更新，卸载也不会回滚已经完成的续期或归属改写

## 投递时间算法

以下算法用于 `cron-up list`、总览的“最近”和预热尾窗估算。它是上游内部实现的复刻，不是 cron-up 自己决定的调度策略

### 任务 id 的归一化值

当前实现对原生十六进制任务 id 取前 8 位，解析后除以 `2^32`，得到 `[0, 1)` 范围内的固定值，记作 `h`。同一 id 每次计算相同，不是每次触发重新随机

手写非标准 id 的解析不应被当作稳定兼容接口；推荐让 CronCreate 生成 id

### 周期任务

对某个 cron 落点，先计算它到下一落点的实际间隔 `period`，再估算：

```text
delay = min(h × 0.5 × period, 30 分钟)
预计投递 = 本落点 + delay
```

每日任务周期较长，很多原生随机 id 会触及 30 分钟上限。落点已经过去、预计投递尚未到来时，仍属于需要会话在场的尾窗，不能按“下一次未来落点”提前回收

代码已记录但**没有复刻**一个上游例外：相邻落点间隔约在 `[300000, 315000)` ms、且表达式匹配上游内部步进规则时，存在 `cacheLeadMs` 提前 15 秒的分支，例如部分约 5 分钟周期任务。对这类任务：

- “周期任务一律在落点后投递”的说法不成立
- 当前 `list` 的预计时间可能与上游实际调度存在约 15 秒或更多的系统性差异
- 是否补齐该分支需要单独实现和测试，不能只改文档宣称已经支持

### 一次性任务

- 落点分钟不属于 `:00`／`:30` 网格时，当前估算不增加投递提前量
- 落点属于网格时，按 `h × 90 秒` 提前，且不早于当前时刻
- 无论是否属于网格，巡检的预热前瞻都统一额外增加 90 秒，原因见生命周期章节

会话内部还存在秒级轮询尾差，因此“预计投递时间”不等于对实际开始执行时刻的保证

### 展示边界

未来落点的展示搜索范围由 `DISPLAY_SEARCH_DAYS` 定义。“一年内无”既包括下一落点超出展示窗口的表达式，例如部分闰日任务，也包括字段可以解析、但日历上永远无法匹配的表达式，例如 `0 0 30 2 *`

“cron 无效”只用于表达式解析失败，或字段值域、区间导致合法值集合为空；它与“一年内无”不是同一状态

## 会话登记、认亲与接管

预热进程的典型结构为：

```text
/usr/bin/script（cron-up state 记录这一层）
  └─ /bin/zsh -lic
      └─ claude（会话登记记录这一层）
```

巡检读取 `~/.claude/sessions/*.json`，结合进程存活、cwd 和祖先链，把 script 进程与登记的 sessionId 对应起来。登记是上游输出，不是稳定 API；读取器包含三类烟雾告警：

- 有登记文件但识别不到 interactive 会话
- 存活登记进程都不是可识别的 `claude`
- interactive 会话缺少有效 pid 或工作目录

这些告警只能覆盖已知漂移形态，不能证明上游所有内部语义均未变化

其他恢复机制：

- **终端接管**：script 层已退出但同一 sessionId 仍在终端存活时，不再另拉或结束该会话
- **孤儿认领**：state 丢失时，按任务专属日志路径从进程表重新识别仍可确认的预热进程
- **停止保护**：发信号前核对进程启动指纹，降低 pid 复用时误伤其他进程组的概率

## 日志与隐私

- 巡检日志位于 `~/Library/Logs/cron-up/launchd.{out,err}.log`，默认 `cron-up logs` 展示当前 stdout 日志最近 100 行
- 会话界面日志按 `<工作区折名>--<任务id>.log` 隔离，启动新代时轮转保留一代 `.1`
- 工作区折名会转义下划线并把路径分隔符折叠为 `_`，避免不同路径轻易撞名
- 会话日志可能包含任务输出，文件按 0600、目录按 0700 管理
- Claude Code 自己仍在 `~/.claude/projects/` 保存对话记录，cron-up 的 `--purge` 不删除这些记录
