# cron-up

为命令行 AI agent 的 cron 定时任务**按任务提前启动并保持一个可用的交互会话**：任务到点时，对应目录里早就有一个开着的 claude 会话，任务一个不少地投进各自的会话执行。平台要求 macOS（依赖 launchd、`script(1)`、zsh）。

> [!WARNING]
> cron-up 建立在 **Claude Code 未公开文档的内部机制**之上（`.claude/scheduled_tasks.json` 格式、会话登记 `~/.claude/sessions/`、逐任务调度谓词与目录级调度锁、任务投递抖动、三代进程结构（已核对本机 **2.1.302**））。这些行为可能随版本变化；看到「会话登记格式疑似变更」类告警，或升级 Claude Code 后任务到点没有会话在场，先核对新版本再继续使用。开头的 WARNING 与各章节的逆向注解，就是给这种时刻准备的。

## 它解决什么问题

在 Claude Code 里用 CronCreate（durable: true）创建的定时任务，记录在工作目录的 `.claude/scheduled_tasks.json` 里。但这些任务**只有在该目录有一个正在运行的交互 claude 会话时才会到点执行**：会话一旦被关掉，周期任务在该会话直接失效；任务到点时没有会话，一次性任务会在下次打开会话时补执行（会话被休眠期间错过的周期任务不会补）。cron-up 是一个由 launchd 每 5 分钟运行一次的巡检进程，逻辑只有一条：**窗口内每个创建者会话已不在的任务，都有一个只属于它的后台会话在该目录等着**。

## 任务级预热：一任务一会话

Claude Code 的任务归属是**任务级**的：任务文件里每条任务各自带 `createdBySessionId`，会话调度器逐任务判定投不投递（2.1.302 二进制核对到的谓词，按优先级）：

1. 任务没有归属会话 → 只有持目录调度锁的会话投；
2. 任务归属的就是本会话 → **无条件投，不需要锁**；
3. 本进程是任务记录的创建者进程（resume 形态）→ 投；
4. 其余情况 → 必须持锁、任务属于本项目、且创建者进程已死，才接管。

cron-up 利用这套规则：为每个「归属会话已死、6 分钟内需要执行」（一次性任务按最早可能投递时刻计，最多再提前 90 秒）的任务单独拉起一个后台会话，并把该任务的归属字段盖成这个新会话。于是同目录多个任务即使同一时刻触发，也各自投进各自的会话、互不插队；任一个预热中途死了，它的任务还会由另一个持锁活会话按规则 4 兜底接管。你本人的交互会话优先级最高：**只要任务的创建者会话还开着，cron-up 完全不碰它**。

| 环节 | 由谁负责 |
|---|---|
| 任务登记 | Claude Code 原生命令 CronCreate，写入工作目录下 `.claude` |
| 定时执行 | Claude Code 交互会话自身（包括补执行和抖动） |
| 保证每个窗口内死主任务有专属会话在场 | cron-up（按任务拉起、盖印、执行完回收） |
| 安装与升级 | npm：`~/Library/LaunchAgents/local.cron-up.plist` 与 `~/.local/share/cron-up/cron-up-service` |

各部分互不影响：卸载 cron-up 后任务依然有效，只是没人保证会话在场。

## 安装

```bash
npm i -g cron-up
cron-up install --roots ~/code,~/work
```

第二步会写入配置与 LaunchAgent 并立即跑首轮巡检；参数都可省略，不带 `--roots` 时沿用现有配置，首次安装默认扫描 `~/space`、`~/workspace`、`~/tasks`。

`--roots` 填写存放 agent 工作目录的父目录（逗号分隔）。不填则默认扫描这三个容器（不存在的跳过），两层以内的目录都能发现任务文件。不扫整个家目录的原因见安全说明。

`launchd` 的环境变量极少（PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`），因此安装时会解析 node 与 cron-up 所在的 bin 目录（fnm/volta/Homebrew/官网安装都支持），把它写进一个自有启动脚本（`cron-up-service`），launchd 每轮从该脚本解析。后台列表里显示 **cron-up-service** 而不是 Node.js 名字。

### 平台要求

- **macOS**（`script(1)`、launchd、zsh 登录 shell）。暂不支持其他系统。
- **Claude Code 2.1 以上**（在 2.1.302 实测；7 天判定与归属字段从 2.1.300 起核对，逐任务谓词与调度锁核对自 2.1.302）。fnm、bun、volta、Homebrew、官网 pkg 与其他版本管理器均支持——安装时把 node 与实际 cron-up 的 bin 目录解析进启动脚本。
- Node.js 22 以上（零运行时依赖，巡检本身只调系统自带工具）。
- 无人值守时的工具权限：后台会话没有人在场点授权确认。后台会话通过 `claude --permission-mode bypassPermissions` 显式以 bypass permissions 模式启动，命令在无人授权下照常执行；目录没走过信任确认、或工具需要二次授权，会话会一直停在提问界面，预热失败后连续失败进入冷却。只把 roots 指向你本人信任的目录。
- 建议在任务描述末尾固定加一句任务结束会话的指令（见下）。

## 日常使用

```bash
cron-up                        # 总览：服务、配置、最近任务、每个预热会话与告警
cron-up list                   # 逐任务列出设定/预计实际触发时间与预热状态
cron-up run                    # 立即手动巡检一次（与定时巡检互斥，同时运行时后到者自动退出）
cron-up logs                   # 查看巡检日志（最近几百行巡检心跳与事件）
cron-up logs team-space        # 查看匹配的后台会话界面记录（多个任务命中时列出候选）
cron-up logs team-space--00000002 -f
cron-up uninstall              # 停止全部预热会话并卸载（配置日志保留；--purge 连产物一起删）
```

巡检固定每 5 分钟一轮、提前 6 分钟为任务备好会话；这些不是可配项。任何任务最迟在执行前一轮巡检被发现；拉起会话后轮内每 3 秒重扫一次会话登记（先扫后睡、至多等 24 秒），健康会话约 10 秒即可完成登记，归属在**同一轮**盖印完成，不再跨一轮。24 秒只是盖印加速的等待上限，不是判死时限：等不到的会话原样留到下轮，仍按跨轮 3 分钟未登记判死，失败计数不因等待而增加。一次性任务在 :00/:30 落点最多提前 90 秒投递，其窗口前沿按最早投递时刻再前推 90 秒，保证任意巡检相位都有一轮在投递前把它发现。

### 自动维护（每轮无条件进行，没有开关）

巡检每轮会顺手维护扫描到的任务文件，全部合并在一次带 mtime 乐观检测的原子写里：

- **自动续期**：给显式周期任务补 `permanent: true`，绕开 Claude Code 的 7 天周期任务回收。
- **自动任务级盖印**：把窗口内死主任务的三个归属字段盖成各自预热会话的身份。只改 `createdBySessionId/createdByPid/createdByProcStart`，不碰 `prompt`、`cron`、`id` 与 `createdInProject`；内容相同但 id 不同的任务仍逐条定位，不会共用盖印目标。

这些维护与 Claude Code 自己对文件的写入（更新 `lastFiredAt`、执行后删一次性任务）用 mtime 做乐观检测：发现撞车就暂缓本轮该文件的写入，下轮再来。它能降低并发覆盖概率，但不是与 Claude Code 共用的互斥锁；最后一次检查与原子替换之间的极小竞态见「已知限制」。

### 让一次性任务结束后自动退出会话

窗口预热会话在任务执行完、界面静默一段时间后自动回收；但推荐在任务描述里要求执行完自己退出，整个过程更干脆：

> 按本仓工作流存好结果后，执行 `/exit` 退出会话。

这样任务结束当刻会话就退出；cron-up 巡检发现任务已离开窗口且会话不在，什么都不用做。即使忘加这句，无人会话也会在执行完并静默后被自动回收，下次窗口重新拉起。

## 窗口轮转与生命周期

预热会话是缓存不是宠物：每个会话只活在「落点前 6 分钟（一次性网格任务至多 7.5 分钟）→ 本任务执行完并静默 3 分钟 → 回收」这一段，任务之间上下文互不累积，内存也只在窗口内占用（每个会话数百 MB，窗口外为零）。回收还要求距该任务下次需要至少 7 分钟——回收后下轮巡检（≤5 分钟）即重新拉起并在当轮完成认亲盖印，余量罩住一次性任务的 90 秒提前投递与唤醒抖动，任务不可能在空档到点。更近的触发直接复用现有会话。

其它生命周期规则：

- **失败冷却**：预热连续 3 次启动失败（通常是缺目录信任、shell 环境损坏），暂停重试 30 分钟，而不是每 5 分钟无限重拉；失败计数按任务各自累积，互不连坐。总览页冷却中的任务合并成一条带排查指引的告警。
- **卡死退休**：会话进程活了 3 分钟仍没在会话登记里出现（停在信任确认或工具授权提问上），终止并按失败处理。
- **终端接管**：你随时可以 `claude --resume <预热会话id>` 把一个预热拉回终端。cron-up 发现原后台进程没了、但同一 sessionId 还活着，就停止管理它：不再另拉、绝不碰你的终端进程；该会话关闭后，任务恢复自动预热。
- **孤儿认领**：state 记录丢失时，巡检能按会话日志路径从进程表里把仍在运行的预热重新认回来。
- **升级迁移**：从目录级单预热的旧版本升级时，首轮巡检会结束能核实身份的旧版预热，之后按任务重新拉起。缺少进程启动指纹的旧条目不会被贸然发信号；若对应进程仍在运行，巡检会明确告警，需人工核查，不会假装已经回收。

## 恢复或接管后台会话

后台会话与普通会话一样保存对话记录，可以在任意终端恢复：

```bash
claude --resume <sessionId>      # 或 claude -r 在列表中选择
```

对话记录在 `~/.claude/projects/<目录编码>/<会话ID>.jsonl`，即使后台进程被结束也能恢复。恢复后该会话如上面「终端接管」所述脱离巡检管理。

## 投递抖动：设定时间与实际触发时间

Claude Code 任务的实际投递不在 cron 落点，而是落点之后加一个按任务 id 确定的偏移（会话内部每秒轮询，实际到点有秒级尾差）。周期任务的延迟 = `min(哈希(id) × 0.5 × 周期, 30 分钟)`，每日任务使用原生随机 id 时几乎必然固定晚到约 30 分钟；一次性任务在 :00/:30 整点最多提前 90 秒。`cron-up list` 的状态列和总览的「最近」显示的是计入抖动后的预计实际时间；cron-up 不改写任务 id，也不会消除这段上游抖动。

巡检判定「任务现在是否需要会话」时，把周期任务落点之后、抖动投递点之前的这段尾窗也算作需要在场，会话不会在任务真正投递前被回收。这些参数逆向自 Claude Code 内部实现，没有稳定性承诺（远程配置键 `tengu_kairos_cron_config` 还能覆盖）；预测与实际系统性偏离时说明上游算法已变。

## 安全说明

- **任务文件是执行输入，root 等同写权限**：任何能在 roots 下写 `.claude/scheduled_tasks.json` 的主体，都登记了一条到点会以你的身份在后台会话里执行的指令。cron-up 读任务文件时严格校验形状，但信任的是文件内容本身——不要把他人可写或共享的目录放进 roots。自动续期还会把扫描到的周期任务补成永久任务，默认 roots 必须是你完全掌控的容器。
- **预热会话拥有你在 Claude Code 中的全部权限**：后台会话通过 `--permission-mode bypassPermissions` 显式以 bypass permissions 模式无人值守运行。roots 的边界就是无人授权写权限的边界。
- **归属盖印会改写任务文件**：cron-up 会改窗口内死主任务的 `createdBySessionId/Pid/ProcStart` 字段。写入采用原子替换（临时文件 0600、保留原文件权限），并用 mtime 乐观检测降低与 Claude Code 并发写入互相覆盖的概率。
- **会话日志可能包含任务输出**：后台会话的界面记录写到 `~/Library/Logs/cron-up/sessions/<工作区>--<任务id>.log`，权限 600、目录 700，每个任务独立文件、轮转保留一代；巡检日志在 `~/Library/Logs/cron-up/`。
- **扫描不深入符号链接的子目录**，默认还排除系统目录与依赖目录。
- **巡检、预热与你的 claude 会话之间不发起网络请求**，也不依赖 npm 注册表；网络活动全部来自被启动的会话本身。唯一的网络发生在安装/升级时访问 npm registry 拉包。

## 已知限制

- 仅支持 macOS。电脑休眠期间错过的周期任务不会补执行（launchd 醒来只补跑一轮巡检）；错过的**一次性**任务会在后台会话启动时补执行。
- 每个窗口内的死主任务对应一个后台会话：同一分钟内有大量任务同时到期时，会同时存在相应数量的会话（每个数百 MB 内存）。时间错开的日常任务只在各自的 6 分钟窗口内占用（一次性任务至多 7.5 分钟）。
- 手工创建的任务若缺少 `createdAt`，错过补执行判定不生效。`cron-up list` 对缺字段的手写任务仍显示「已错过/设定时间」，但预热与补执行依赖 Claude Code 与 cron-up 的字段纪律。
- 工作区从巡检视野里消失（`.claude/scheduled_tasks.json` 被整个删除或移出 roots）后，仍在运行的预热不会被回收，总览会列出这类会话，不需要时手动结束。
- 任务文件的 mtime 乐观检测不是跨进程 CAS：另一个写者若恰好赶在最后一次检查之后、原子替换之前写入，仍可能被覆盖。这个窗口无法由 cron-up 单方面彻底关闭；需要绝对保证时，应由上游提供共享写锁或公开写接口。
- 预热依据的逐任务谓词、调度锁与三代进程结构是未公开内部实现：新版若调整归属/锁语义，任务级隔离的前提需要重新核对。cron-up 保留了会话登记格式的烟雾告警，格式漂移时在总览页明示。

## 故障排查

| 现象 | 排查方法 |
|---|---|
| 总览提示「冷却中」 | 运行 `cron-up logs <目录>--<任务id>` 查看启动界面：停在信任确认就先在该目录手动走完信任；shell 初始化缺命令（command not found）按「启动脚本 PATH」段修 |
| 任务到点没有执行 | `cron-up list` 看任务与预热状态；预热在则看它的会话日志；总览的「需要留意」按任务给出原因 |
| 总览提示「启动脚本已失效 / PATH 找不到 node」 | 重跑 `cron-up install`（见下） |
| 总览提示「巡检已沉默」 | launchd 显示加载但心跳超时：先 `cron-up logs`，再重跑 install |
| `last exit code=2` | 配置损坏或字段类型不对：修好 `~/.local/share/cron-up/config.json`（只有 roots 一个字段）或重跑 install |
| 手动 `cron-up run` 正常、定时执行不正常 | 手动测试继承终端 PATH，定时由启动脚本驱动；换过 Node 安装方式后重跑 install |
| 任务表显示「已错过」 | 一次性任务落点已过：后台会话一启动就会补执行；周期任务没有补执行 |
| 日志里出现「卡死」 | 会话 3 分钟没完成登记：信任确认/工具授权提问没人应答，手动进目录走一遍授权 |
| 同目录多个任务互相干扰 | 升级后首轮会结束旧版目录级预热；如仍异常，确认所有预热会话都由新版本拉起（日志名含 `--任务id`） |

## 维护

- **修改扫描范围**：`cron-up install --roots "$HOME/code,$HOME/work"`。重跑 install 会重写配置（旧版本留下的废弃字段一并纯化）、启动脚本与 LaunchAgent。
- **升级**：`npm i -g cron-up@latest` 后重跑一次 `cron-up install`。下一轮巡检自然跑新版；Node 版本与包文件在 install 后自动跟随。fnm 切换默认版本同理。
- **版本号**：总览首行、心跳文件都带版本；发版收尾跑一次无参数 `cron-up` 确认首行版本、服务已加载且退出码 0、「需要留意」为空。

### 配置文件

配置只有扫描范围一个字段：`~/.local/share/cron-up/config.json`

```json
{ "roots": ["/Users/you/code", "/Users/you/work"] }
```

间隔（300 秒）、提前量（360 秒，一次性任务另加至多 90 秒）、扫描深度（3）、轮内等待认亲上限（24 秒）都是固定常量；直接编辑文件改 roots 也可以，最多 5 分钟后的下轮巡检生效。字段损坏时巡检响亮失败（退出码 2），不静默回退。

| 产物 | 位置 |
|---|---|
| 命令行与代码 | npm 全局目录（fnm 为 `~/.local/share/fnm/aliases/default/...`） |
| 配置文件 | `~/.local/share/cron-up/config.json` |
| 运行状态 | 同目录 `state.json`（按工作区与任务 id 两级记录预热） |
| 配置心跳 | 同目录 `heartbeat`（每轮写一次） |
| LaunchAgent | `~/Library/LaunchAgents/local.cron-up.plist` |
| 启动脚本 | `~/.local/share/cron-up/cron-up-service` |
| 巡检日志 | `~/Library/Logs/cron-up/launchd.{out,err}.log` |
| 各任务会话日志 | `~/Library/Logs/cron-up/sessions/<工作区>--<任务id>.log`（轮转保留一代 `.1`） |

## 开发与测试

```bash
git clone git@github.com:adaex/cron-up.git && cd cron-up
node --test                 # 全部测试（需要 Node 22+；零依赖）
npm link                    # 本机把开发版链接成全局 cron-up
```

`bin/cron-up.mjs` 是 CLI 入口，`src/` 是各业务模块，通过 `src/internals.mjs` 的 deps 容器注入外部依赖（便于测试打桩）。测试与源码同量，改行为请同步改测试。

## 发布

- **版本号**：按「年.月.序号」——两位年份、两位月份、累计发布序号（0.x 时代的发布总数，含 0.x，序号永不重置、不随月份归零，始终等于含本次在内的历史发布总次数）。下一序号不用手数：发布前 `git fetch --prune --prune-tags --tags` 后数 v* tag 总数加一，`prune-tags` 让删错的 tag 不计数。
- **发布方式**：先把 package.json 的 version 改成新版本并合入 main，再创建同名签名注解 tag 并推送：`git tag -s v<version> <发布提交> -m "发布 <version>"`、`git push origin v<version>`；GitHub Actions 会跑通测试（Node 22/24）、校验 package.json 版本与 tag 一致（不符直接失败）、并 publish。tag 失败的 launchd 入口旧 tag 重跑即可，序号不消耗。发布失败的 tag 重跑 release 工作流即可，序号不消耗。
- npm 经 GitHub OIDC 验证「确为 `adaex/cron-up` 仓库 `v` 触发的运行」后放行，仓库里没有 NPM_TOKEN，token 泄漏这条路不存在。
- **发版收尾**（每次发版必做）：逐台升级已有安装，在每台机器用显式新版本号加 `--prefer-online` 安装后重跑一次 `cron-up install`，再跑无参数的 `cron-up`，确认首行是刚发的版本号、服务已加载且上次退出码 0、「需要留意」为空。未安装的机器不借升级新装；连不上的机器明确记为未完成，不能以 npm 发布成功代替逐机核实。
- **npm 传播延迟**：publish 成功后到 registry 可查通常两分钟、偶发七八分钟（带 provenance 要等透明日志与后端入库），本机元数据缓存还会再滞后，直接 `npm i -g cron-up` 可能装回旧版且毫无提示——用显式版本号加 `--prefer-online` 安装（`npm i -g cron-up@<新版本> --prefer-online`），装完以总览首行版本号为准。
- **trusted publishing**：npm 包设置页里已登记 GitHub 仓库（repository `adaex/cron-up`，workflow `release.yml`），一次性配置，没了见 Trusted Publisher 文档。
