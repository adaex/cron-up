# cron-up

为 **Claude Code 的 durable 定时任务**在触发前按需预热交互会话，减少因原会话关闭、电脑上没有在线会话而造成的漏跑。每个需要 cron-up 预热且能唯一识别的任务使用独立后台会话，任务仍由 Claude Code 自己投递和执行

目前仅支持 macOS，依赖 launchd、Herdr Core 和 zsh；不是通用命令行 AI agent 的调度器。会话按任务需要创建，满足回收条件后退出，短周期任务也可能持续复用现有会话

所有预热会话都由 Herdr 管理，可以在 Herdr 中查看、接管和读取历史；`hc` 是必需依赖

> [!WARNING]
> cron-up 依赖 Claude Code 未公开且无稳定性承诺的内部实现。当前核心行为以 **2.1.302** 的本机核对结果为依据，其他版本不代表已经验证；不同机制的核对版本见[内部机制与兼容性](docs/internals.md)。升级 Claude Code 后，先运行 `cron-up` 查看告警，再确认任务能正常预热和投递

## 它解决什么问题

在 Claude Code 中用 CronCreate 创建 `durable: true` 的任务后，任务记录在当前工作目录的 `.claude/scheduled_tasks.json` 中。任务到点时，该目录需要有正在运行的交互 `claude` 会话：

- 原创建者会话还开着时，任务优先投递给它，cron-up 不为其预热或改写归属
- 原创建者会话已经关闭时，cron-up 在任务进入预热窗口后尝试启动专属后台会话，并改写该任务的归属字段
- 电脑休眠期间错过的周期任务不会补执行；一次性任务的补执行见[任务时间与执行](#任务时间与执行)

职责边界如下：

| 环节 | 负责方 |
| --- | --- |
| 创建和保存任务 | Claude Code 的 CronCreate 工具 |
| 判断触发时刻、投递 prompt、执行任务 | Claude Code 交互会话 |
| 提前准备会话、调整任务归属、回收会话 | cron-up |
| 定时驱动巡检 | macOS launchd |

cron-up 不负责创作任务内容，也不能保证每个任务都执行成功。授权、模型、工具、任务脚本和上游调度仍可能失败

### 核心行为

- **自动补 `permanent`、自动改小周期任务 ID 是最强约束**：对所有具有有效 ID 的显式周期任务每轮无条件执行，没有任务级或全局开关，也不依赖原创建者会话是否在线
- **一任务一个 Claude 会话**：不为减少进程数而合并不同任务的会话。当前采用长期保留，在下一代预热启动前按规则关闭上一代；不会仅因界面静默几分钟就提前回收。未来若探索 idle 一小时等短期回收，只改变回收时机，不改变一任务一会话模型
- **命名锚点是临时方案**：它只用于弥补当前 hc 不能直接创建、命名 space 并设置所需目录的能力缺口；hc 原生支持后应删除锚点，不把它发展成长期的空间管理层。真实任务终端的固定归组不受影响

## 安装前须知

### 环境与兼容性

- **macOS**：使用 launchd 和 zsh，暂不支持其他系统
- **Node.js 22 或更高版本**：cron-up 没有 npm 第三方运行时依赖
- **Claude Code**：核心行为已在 2.1.302 核对；更低或更高版本均应按未验证版本对待，不要仅凭版本号推断兼容。`--name` 会话命名与终端标题链路已在 2.1.319 单独核对，详见[内部机制与兼容性](docs/internals.md)
- **Herdr Core**：`PATH` 或 `~/.local/bin/hc` 中必须有可执行的 `hc`；当前已在 0.1.18 核对，其他版本按未验证处理。install 会把实际找到的 `hc` 所在目录写入 cron-up 服务的 `PATH`
- **可用的 `claude` 命令**：已完成登录和所需配置，并且能从交互登录 zsh 中启动；可先用 `zsh -lic 'command -v claude'` 检查
- **目录信任与工具授权**：先在该工作目录手动启动一次 Claude Code，完成信任确认及无法在无人值守时回答的授权，否则预热可能停在提问界面，随后被判为卡死并进入失败流程

fnm、volta、Homebrew、官网 pkg 等 Node 安装方式均可用于提供 `node`。nvm 等把 Node 放在版本目录中的安装方式，在切换或删除版本后需要重新运行 `cron-up install`；这里说的是 Node 的启动链，不代表所有 Claude Code 安装和 shell 配置都经过验证

### 安全与自动修改

> [!CAUTION]
> `roots` 是**任务扫描与信任范围，不是沙箱**。cron-up 不传 `--permission-mode`，后台会话以当前 macOS 用户身份运行，权限模式遵循 Claude Code 自身配置；配置为自动执行或跳过确认时，任务可在无人值守时调用工具。任务可以访问 roots 之外的位置，也可能通过模型、MCP 或任务工具联网

只扫描你信任其**整个工作区内容**的目录，而不只是检查任务文件。预热会在工作区启动完整的 Claude Code，任务、`CLAUDE.md`、`.claude` 中的项目指令与配置，以及任务可能调用的脚本，都可能影响无人值守会话

目录归你所有并不等于内容可信：clone 到 roots 下的外部仓库、团队共享仓库或他人可写目录，都可能带来由他人编写的任务和项目指令，不能只审核 `.claude/scheduled_tasks.json`

安装后，每轮巡检会按需自动维护扫描到的任务文件：

1. 给所有具有有效 ID 的显式周期任务补 `permanent: true`，使其绕开 Claude Code 的 7 天周期任务回收
2. 把这些周期任务的随机大 ID 改成任务文件内未占用的小号（`00000001` 起），消除 Claude Code 按 ID 计算的周期投递延迟；一次性任务和无 ID 条目不维护
3. 对已经进入预热窗口、原归属会话不在场的任务，改写 `createdBySessionId`、`createdByPid` 和 `createdByProcStart`

这些行为没有任务级开关，自动续期和周期任务 ID 改小也不依赖原创建者会话是否在线。手动删除 `permanent` 或把周期任务改回随机大 ID 后，只要任务仍在扫描范围内，后续巡检还会补回或重新改小。不希望某个工作区被修改时，应把它移出 roots；已经写入的字段不会自动恢复，详见[卸载与数据保留](#卸载与数据保留)

## 快速开始

### 1. 安装并选择扫描范围

```bash
npm i -g cron-up
cron-up install --roots ~/code,~/work
```

`--roots` 接受逗号分隔的目录列表，每次提供的是完整列表，不是在原列表上追加。第二步会写入配置、启动脚本和 LaunchAgent，并立即尝试首轮巡检

不带 `--roots` 时会沿用可读取且 roots 类型有效的现有配置；首次安装使用默认范围 `~/space`、`~/workspace`、`~/tasks`，不存在的目录会跳过。使用默认范围前，同样要确认其中现在及未来出现的任务和项目指令都可信

已有配置无法解读时，不带 `--roots` 的 install 会停止，不会回退默认范围并扩大自动写入；必须直接修复配置，或显式提供完整 roots，详见[配置无法解读时](#配置无法解读时)

扫描范围按下面的路径深度计算：

- root 本身，以及 root 下的第 1、2、3 层目录都会检查任务文件
- 例如 `<root>/<repo>/<subdir>/<nested>` 是 root 下第 3 层，可以发现；再深一层不会发现
- 不深入符号链接形式的子目录，并跳过依赖目录和常见系统目录，完整名单见 `src/constants.mjs` 中的 `PRUNE_DIRS`

工作区指**包含 `.claude/scheduled_tasks.json` 的那个精确目录**，不自动等同于 Git 仓库根目录。若任务是在仓库子目录的 Claude Code 会话里创建，它属于该子目录

### 2. 创建第一个任务

进入 roots 覆盖的工作目录并启动 Claude Code，然后在 Claude Code 中提出请求，例如：

> 在当前工作目录用 CronCreate 创建一个 `durable: true` 的一次性任务，约 5 分钟后在会话里回复“cron-up 验证成功”

CronCreate 是 Claude Code 内部工具，不是在终端里直接执行的 shell 命令。当前由 cron-up 按生命周期保留和回收会话，不要求任务执行 `/exit`；已经完成登记的会话主动退出也不等同于启动失败，后续是否重新预热仍由任务窗口决定

### 3. 验证发现和预热

依次用 `cron-up list` 确认任务已被发现并查看时间，用 `cron-up run` 立即巡检一次，再用 `cron-up` 查看服务、会话和告警。需要查看后台界面时，运行 `cron-up logs <目录名或任务id>`；完整命令和日志选项见[日常使用](#日常使用)

定时巡检每 5 分钟一轮。周期任务在设定时间前 6 分钟进入预热窗口；所有一次性任务都统一再增加 90 秒前瞻，最早可在设定时间前 7.5 分钟进入窗口。实际启动由窗口内的巡检触发，具体时间取决于巡检相位，并不是固定提前 6 或 7.5 分钟

其中，落在 `:00` 或 `:30` 的一次性任务按当前上游规则还可能提前至多 90 秒投递

任务还没到预热窗口时，`cron-up run` 不会为它提前常驻一个会话；若已经有一轮巡检在运行，后到的一轮会跳过

## 日常使用

```bash
cron-up                        # 总览：服务、配置、最近任务、预热会话与告警
cron-up list                   # 列出所有工作区的任务时间、摘要、模型配置与预热状态
cron-up run                    # 立即手动巡检一次
cron-up logs                   # 查看最近 100 行巡检日志
cron-up logs team-space        # 查看匹配的后台会话
cron-up logs 00000002 -f       # 接入活跃的匹配会话
```

无参数时查看巡检日志。给出匹配片段时，会话可以按目录名、任务 id、Herdr 地址或显示标题查找；命中多个时会列出候选，请补充更长的片段。会话历史使用 `hc read`，`-f` 对活跃会话改为 `hc attach`

### 在 Herdr 中查看预热会话

每次预热都会创建一个独立的 Herdr 终端，固定归入 `cron-tasks` space，并用任务 prompt 的首个非空行设置会话标题。可以用 `hc ls` 查看，用 `hc attach <地址>` 接入，按 `Ctrl+\` 脱离；终端地址也会记录在巡检日志中

命名锚点只是当前 hc 能力不足时的临时方案。只有确实要新建 Claude 会话前才检查锚点；平静巡检、复用、原创建者在线和孤儿认领都不会查询或补建。锚点只是普通 zsh，不启动 Claude，准备失败不阻塞任务预热；hc 原生支持后删除

任务终端通过 `/bin/zsh -lic` 启动，沿用交互 shell 中的 Claude 命令和配置。终端保持独立，退出或被回收后历史仍由 Herdr 保留，可以继续用 `cron-up logs <匹配片段>` 查看

cron-up 只通过 `hc` 操作 Herdr Core，不调用 App 能力。机器标签、标题兼容、锚点命名及停止前身份核验见[内部机制](docs/internals.md#herdr-启动层)

### 看懂总览和任务列表

总览优先看以下信息：

- **服务与上次巡检**：launchd 已加载不等于巡检仍在成功运行，心跳可以帮助识别启动链失效
- **最近**：按 cron 设定落点排序；尾窗中只提示设定时间已到，不预测实际投递秒数
- **需要留意**：配置、启动链、会话登记、预热失败和失去扫描范围的会话等告警

下面是 `cron-up list` 的输出格式示例，日期、时间和 pid 以本机实际输出为准：

```text
共 1 个工作区、2 个定时任务

~/code/my-project
  10-24 19:52          一次性      52 19 24 10 *     验证 cron-up [预热中 12345]
  10-25 09:00          周期·永久   0 9 * * *         每日汇总
```

工作区位于家目录下时，块首路径优先显示为 `~/…`，例如 `~/space/infra-space`；家目录外仍显示绝对路径。这只改变展示，内部扫描和会话认领仍使用绝对路径

常见状态和标签：

| 显示 | 含义 |
| --- | --- |
| 时间列 | 显示 cron 设定落点，不是实际投递承诺；延迟尾窗中仍显示本次待投递的落点 |
| `启动中 <pid>` | 会话进程已启动，尚未在 Claude Code 会话登记中确认 |
| `预热中 <pid>` | 已确认后台会话登记且预热进程存活；归属是否已写回可结合巡检日志判断 |
| `待预热` | 已进入预热窗口，但当前还没有承接会话；结合总览告警判断原因 |
| `冷却中` / `失败N次` | 预热启动失败，正在退避或已经累计失败；修复环境后等待自动重试 |
| `终端接管` | 用户通过 `--resume` 接管了该会话，cron-up 不再另拉或结束它 |
| 标签为空 | 可能还没到预热窗口，也可能原创建者会话仍在线，需要结合时间列和总览判断 |
| `已错过` | 一次性任务的设定时间已经过去；有效 `createdAt` 是 cron-up 判断错过待补的必要字段 |
| `一年内无` | cron 可解析，但 366 天展示窗口内没有未来落点；二月三十日这类日历上永远不出现的表达式也归入此状态 |
| `无ID不调度` | 手写条目缺少非空字符串 id，巡检不维护也不预热；通过 CronCreate 重建 |
| `cron 无效` | 表达式解析失败，或字段值域、区间导致合法值集合为空，巡检会跳过该任务 |

## 任务时间与执行

文档和命令输出均使用 macOS 本机时间。`list` 和总览只显示 **cron 设定落点**，不提供秒级预计投递时间；Claude Code 的实际投递与执行仍可能提前或延后

周期任务的原生随机 ID 可能带来按 ID 计算的投递偏移，cron-up 每轮自动改小 ID 以消除这段偏移；已经运行的会话可能要到下一代启动后才完全使用新 ID。一次性任务落在 `:00` 或 `:30` 时还可能提前至多 90 秒，因此预热窗口会统一多留 90 秒

电脑休眠期间，launchd 醒来后只补跑一轮巡检：错过的周期任务不会补执行；错过的一次性任务通常会在后台会话启动时由 Claude Code 补执行，缺少有效 `createdAt` 时无法识别这种补执行

上游窗口规则、已知例外和展示边界见[内部机制](docs/internals.md#投递时间算法)

## 会话生命周期与恢复

- 每个任务使用独立 Claude 会话。本代任务触发后，会话保留到下一代预热窗口；下一代启动前按规则结束上一代，不会仅因界面静默几分钟就提前回收
- 新会话启动失败会按任务计数，连续失败后暂时冷却；修复环境后等待自动重试。已登记会话主动退出只记录事实，未登记就退出才按启动异常提示排查
- 高频任务没有独立换代间隙时会继续复用会话；同分钟多个任务会同时拉起多个 Claude 进程，低频会话保留期间也持续占用内存

后台会话可以在终端用 `claude --resume <sessionId>` 恢复。若原后台进程已经退出而同一 sessionId 仍在终端运行，cron-up 会停止管理它，不结束用户终端；该会话关闭后，后续巡检可以重新预热

登记等待、卡死、换代条件与失败老化等完整规则见[内部机制](docs/internals.md#巡检与会话生命周期)

## 自动维护的写入边界

同一轮中的自动续期、周期任务 ID 改小和归属改写会合并为带 mtime 乐观检测的原子写入；检测到 Claude Code 同时修改任务文件时，本轮写入暂缓，后续重试

每次改号都会在巡检日志中逐任务记录「工作区、任务摘要、旧 ID → 新 ID」。改号后按新 ID 操作，旧新对应关系可从当轮日志查证

这不是与 Claude Code 共用的互斥锁，仍存在极小竞态窗口，详见[内部机制](docs/internals.md#任务文件维护与并发)。卸载 cron-up 不会撤销已经写入任务文件的修改

## 配置与产物

配置文件为 `~/.local/share/cron-up/config.json`，只有扫描范围一个字段：

```json
{ "roots": ["/Users/you/code", "/Users/you/work"] }
```

可以直接编辑 roots，通常最多等下一轮巡检生效；也可以运行：

```bash
cron-up install --roots "$HOME/code,$HOME/work"
```

重跑 install 会重写配置、启动脚本与 LaunchAgent

巡检间隔、提前量、扫描深度、失败退避等均为固定行为，完整常量和生命周期规则见[内部机制](docs/internals.md#巡检与会话生命周期)

### 按工作区指定模型

在工作区放置可选的 `.claude/cron-up.json`，统一指定该目录所有新预热会话的模型：

```json
{ "model": "claude-opus-5-5" }
```

省略 `model` 时不传 `--model`，沿用 Claude Code 自身配置。模型值由本机 Claude Code 解释，cron-up 不维护模型清单，也不提前验证模型是否可用

配置只影响之后新启动的预热会话，不重启或切换已有会话，也不改变仍在线的原创建者会话。JSON 损坏或 `model` 类型不对时会暂停该工作区的新预热，但不影响自动续期、周期任务 ID 改小和已有会话管理

旧版 `tasks.<任务id>.model` 覆盖已不再支持；存在 `tasks` 字段时会明确告警，请删除该字段，只保留顶层 `model`，避免静默使用错误模型

此文件完全由用户维护，巡检、install、uninstall 和 `--purge` 都不会创建、修改或删除它

| 产物 | 位置 |
| --- | --- |
| 命令行与代码 | npm 全局目录，具体位置取决于 Node 与 npm 安装方式 |
| 配置文件 | `~/.local/share/cron-up/config.json` |
| 工作区模型配置（可选） | `<工作区>/.claude/cron-up.json`，只有顶层 `model`，完全由用户维护 |
| 运行状态 | `~/.local/share/cron-up/state.json`，按工作区与任务 id 记录预热 |
| 巡检心跳 | `~/.local/share/cron-up/heartbeat`，每轮成功完成后写入 |
| LaunchAgent | `~/Library/LaunchAgents/local.cron-up.plist` |
| 启动脚本 | `~/.local/share/cron-up/cron-up-service` |
| 巡检日志 | `~/Library/Logs/cron-up/launchd.{out,err}.log` |
| Herdr 会话界面与历史 | 由 Herdr Core 管理，cron-up 不另写会话日志 |
| Claude Code 对话记录 | `~/.claude/projects/<目录编码>/<会话ID>.jsonl`，由 Claude Code 管理 |

Herdr 会话的界面与历史可能包含任务输出，其保存位置和权限由 Herdr 管理；cron-up 的 `--purge` 不删除这些记录

巡检日志会记录版本、进入窗口时不另拉会话的原因、登记对应的 sessionId 与进程、逐任务过户，以及当轮等待后仍未登记的情况。这些日志只记录会话管理，不证明任务执行成功；任务是否完成、是否等待人工回答，仍要结合对应会话日志与 Claude Code 对话记录判断

cron-up 自身的巡检和会话管理不主动访问 npm registry 或其他网络服务；安装和升级时由 npm 访问 registry。被启动的 Claude Code 会话仍可能联网，cron-up 不对其网络活动作限制

### 配置无法解读时

不带 roots 重跑 install 时，只有可读取且 roots 类型有效的现有配置才会被沿用。已有配置存在但无法解读时，install 会以退出码 2 停止，不修改配置或 LaunchAgent，也不执行本次 install 的首轮巡检；不会回退到默认范围 `~/space`、`~/workspace`、`~/tasks`，因为这可能突然扩大自动续期、改号和其他任务文件写入的范围

修复时可以直接改正上述配置文件，再重跑 install；也可以显式传入完整的 `--roots` 重建。只有首次安装、没有现有配置时，不带 roots 才使用默认范围

## 升级与启动链维护

升级 cron-up：

```bash
npm i -g cron-up@latest --prefer-online
cron-up install
cron-up
```

最后一步确认首行版本、launchd 状态、上次退出码和“需要留意”。刚发布新版本时 registry 与本机缓存可能有延迟，维护者发版后的逐机升级使用显式版本号，见[发布后的逐机升级与验收](docs/release.md#每次发版后的逐机升级与验收)

launchd 的初始 PATH 很小，因此 install 会把 `node`、`cron-up` 与实际找到的 `hc` 所在 bin 目录写入 `~/.local/share/cron-up/cron-up-service`。预热中的 `claude` 则由 Herdr 终端里的 `/bin/zsh -lic` 启动，依赖登录交互 shell 的配置，而不是仅靠前述目录

出现以下情况后应重跑 `cron-up install`：

- 切换、删除或更换 Node 安装方式
- 修改 roots 或需要重建 LaunchAgent
- 总览提示启动脚本失效、PATH 找不到 node／cron-up，或巡检心跳沉默

若 `zsh -lic 'command -v claude'` 失败，先修复交互 zsh 中的 `claude` 命令及其环境，再重跑 install。手动 `cron-up run` 成功而 launchd 失败时，也应优先比较这两种环境的差异

## 卸载与数据保留

`cron-up uninstall` 管理的是本机服务和 cron-up 自有产物，不等于删除所有相关数据：

| 操作或数据 | `cron-up uninstall` | `cron-up uninstall --purge` |
| --- | --- | --- |
| 停止仍可安全跟踪的预热会话与命名锚点 | 是 | 是 |
| 移除 LaunchAgent 和 plist | 是 | 是 |
| 删除 `/tmp/cron-tasks` 锚点目录 | 否 | 否，由系统按临时目录规则清理 |
| 删除 `~/.local/share/cron-up` 中的配置、状态、心跳和启动脚本 | 否 | 是 |
| 删除 `~/Library/Logs/cron-up` 中的巡检日志 | 否 | 是 |
| 删除 Herdr 保存的预热终端历史 | 否 | 否 |
| 卸载 npm 全局 `cron-up` 命令 | 否 | 否 |
| 删除 Claude Code 任务或 `~/.claude/projects` 对话记录 | 否 | 否 |
| 删除各工作区的 `.claude/cron-up.json` | 否 | 否 |
| 恢复任务文件中的 `permanent`、`createdBy*` 字段 | 否 | 否 |

完全移除命令行和 cron-up 自有产物：

```bash
cron-up uninstall --purge
npm uninstall -g cron-up
```

Claude Code 任务和对话记录需要在 Claude Code 侧另行处理。卸载后任务文件仍然存在，但 cron-up 不再提供预热、续期、周期任务 ID 改小或会话回收；不要把这个状态理解为任务字段已经恢复原状

## 故障排查

| 现象 | 排查方法 |
| --- | --- |
| 总览提示“冷却中” | 运行 `cron-up logs <目录名或任务id>` 查看启动界面；常见原因是目录信任、工具授权、登录状态或 shell 环境。修复后等待自动重试；冷却结束本身不代表问题已经修复 |
| 设定时间到了但没有执行 | 上游投递可能提前或延后，先看总览是否提示等待上游投递，再看对应会话日志，并确认当时电脑没有休眠；`list` 的设定落点不是实际执行承诺 |
| 总览提示“启动脚本已失效 / PATH 找不到 node 或 hc” | 按[升级与启动链维护](#升级与启动链维护)检查并重跑 `cron-up install` |
| 总览提示“巡检已沉默” | 先运行 `cron-up logs` 查看巡检和 stderr 提示，再检查启动链并重跑 install |
| `last exit code=2` | 通常是配置损坏或 roots 类型不对；直接修复 `~/.local/share/cron-up/config.json`，或按[配置无法解读时](#配置无法解读时)的说明显式传入完整 roots 重跑 install |
| 手动 `cron-up run` 正常、定时执行不正常 | 比较终端与 launchd／`zsh -lic` 的 PATH、Node 和 `claude` 环境；换过 Node 安装方式后重跑 install |
| 任务表显示“已错过” | 对一次性任务检查后台会话是否启动及其日志；手写任务缺少有效 `createdAt` 时，cron-up 不会按错过待补处理 |
| 日志里出现“卡死” | 表示超过登记宽限后由巡检终止，常见于人工作答界面，也可能是会话登记或启动形态变化；先看会话日志和总览的登记格式告警 |

## 已知限制

- 仅支持 macOS，且依赖未公开的 Claude Code 内部实现；上游升级可能改变任务归属、登记格式、进程结构和投递算法
- 电脑休眠期间错过的周期任务不会补执行；一次性任务的补执行依赖上游机制和必要任务字段
- 每个进入窗口且原归属不在场的任务对应一个会话，同分钟大量任务可能带来明显内存压力
- 只调度具有唯一非空字符串 id 的任务；无 id 的手写条目会显示并跳过，不生成匿名身份。一次性任务还需要毫秒时间戳 `createdAt` 才能判断错过待补
- 工作区的任务文件被整体删除或目录移出 roots 后，仍在运行的预热可能不再被回收；总览会列出能识别的此类会话，需要人工处理
- mtime 乐观检测不能完全关闭跨进程写入竞态；需要绝对写入保证时，应由上游提供共享锁或公开写接口
- 即使预热和投递正常，任务仍可能因模型、工具、权限、网络或 prompt 本身而失败
