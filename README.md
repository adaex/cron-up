# cron-up

为 **Claude Code 的 durable 定时任务**在触发前按需预热交互会话，减少因原会话关闭、电脑上没有在线会话而造成的漏跑。每个需要 cron-up 预热且能唯一识别的任务使用独立后台会话，任务仍由 Claude Code 自己投递和执行

目前仅支持 macOS，依赖 launchd、`script(1)` 和 zsh；不是通用命令行 AI agent 的调度器。会话按任务需要创建，满足回收条件后退出，短周期任务也可能持续复用现有会话

> [!WARNING]
> cron-up 依赖 Claude Code 未公开且无稳定性承诺的内部实现。当前核心行为以 **2.1.302** 的本机核对结果为依据，其他版本不代表已经验证；不同机制的核对版本见[内部机制与兼容性](docs/internals.md)。升级 Claude Code 后，先运行 `cron-up` 查看告警，再确认任务能正常预热和投递

## 它解决什么问题

在 Claude Code 中用 CronCreate 创建 `durable: true` 的任务后，任务记录在当前工作目录的 `.claude/scheduled_tasks.json` 中。任务到点时，该目录需要有正在运行的交互 `claude` 会话：

- 原创建者会话还开着时，任务优先投递给它，cron-up 不为其预热或改写归属
- 原创建者会话已经关闭时，cron-up 在任务进入预热窗口后尝试启动专属后台会话，并改写该任务的归属字段
- 电脑休眠期间错过的周期任务不会补执行；一次性任务的补执行见[任务时间与执行](#任务时间与执行)

职责边界如下：

| 环节 | 负责方 |
| --- | --- |
| 创建和保存任务 | Claude Code 的 CronCreate 工具 |
| 判断触发时刻、投递 prompt、执行任务 | Claude Code 交互会话 |
| 提前准备会话、调整任务归属、回收会话 | cron-up |
| 定时驱动巡检 | macOS launchd |

cron-up 不负责创作任务内容，也不能保证每个任务都执行成功。授权、模型、工具、任务脚本和上游调度仍可能失败

## 安装前须知

### 环境与兼容性

- **macOS**：使用 launchd、`script(1)` 和 zsh，暂不支持其他系统
- **Node.js 22 或更高版本**：cron-up 没有第三方运行时依赖
- **Claude Code**：核心行为已在 2.1.302 核对；更低或更高版本均应按未验证版本对待，不要仅凭版本号推断兼容
- **可用的 `claude` 命令**：已完成登录和所需配置，并且能从交互登录 zsh 中启动；可先用 `zsh -lic 'command -v claude'` 检查
- **目录信任与工具授权**：先在该工作目录手动启动一次 Claude Code，完成信任确认及无法在无人值守时回答的授权，否则预热可能停在提问界面，随后被判为卡死并进入失败流程

fnm、volta、Homebrew、官网 pkg 等 Node 安装方式均可用于提供 `node`。nvm 等把 Node 放在版本目录中的安装方式，在切换或删除版本后需要重新运行 `cron-up install`；这里说的是 Node 的启动链，不代表所有 Claude Code 安装和 shell 配置都经过验证

### 安全与自动修改

> [!CAUTION]
> `roots` 是**任务扫描与信任范围，不是沙箱**。后台会话通过 `claude --permission-mode bypassPermissions` 跳过工具权限确认，并以当前 macOS 用户身份运行；任务可以访问 roots 之外的位置，也可能通过模型、MCP 或任务工具联网

只扫描你信任其**整个工作区内容**的目录，而不只是检查任务文件。预热会在工作区启动完整的 Claude Code，任务、`CLAUDE.md`、`.claude` 中的项目指令与配置，以及任务可能调用的脚本，都可能影响无人值守会话

目录归你所有并不等于内容可信：clone 到 roots 下的外部仓库、团队共享仓库或他人可写目录，都可能带来由他人编写的任务和项目指令，不能只审核 `.claude/scheduled_tasks.json`

安装后，每轮巡检会按需自动维护扫描到的任务文件：

1. 给所有显式周期任务补 `permanent: true`，使其绕开 Claude Code 的 7 天周期任务回收
2. 对已经进入预热窗口、原归属会话不在场的任务，改写 `createdBySessionId`、`createdByPid` 和 `createdByProcStart`

这些行为没有任务级开关。即使原创建者会话仍在线，自动续期仍会进行；手动删除 `permanent` 后，只要任务仍在扫描范围内，后续巡检还会补回。不希望某个工作区被修改时，应把它移出 roots；已经写入的字段不会自动恢复，详见[卸载与数据保留](#卸载与数据保留)

## 快速开始

### 1. 安装并选择扫描范围

```bash
npm i -g cron-up
cron-up install --roots ~/code,~/work
```

`--roots` 接受逗号分隔的目录列表，每次提供的是完整列表，不是在原列表上追加。第二步会写入配置、启动脚本和 LaunchAgent，并立即尝试首轮巡检

不带 `--roots` 时会沿用可读取且 roots 类型有效的现有配置；首次安装使用默认范围 `~/space`、`~/workspace`、`~/tasks`，不存在的目录会跳过。使用默认范围前，同样要确认其中现在及未来出现的任务和项目指令都可信

现有配置无法解读时也会回退默认范围；其写入风险和修复方法见[配置无法解读时](#配置无法解读时)

扫描范围按下面的路径深度计算：

- root 本身，以及 root 下的第 1、2、3 层目录都会检查任务文件
- 例如 `<root>/<repo>/<subdir>/<nested>` 是 root 下第 3 层，可以发现；再深一层不会发现
- 不深入符号链接形式的子目录，并跳过依赖目录和常见系统目录，完整名单见 `src/constants.mjs` 中的 `PRUNE_DIRS`

工作区指**包含 `.claude/scheduled_tasks.json` 的那个精确目录**，不自动等同于 Git 仓库根目录。若任务是在仓库子目录的 Claude Code 会话里创建，它属于该子目录

### 2. 创建第一个任务

进入 roots 覆盖的工作目录并启动 Claude Code，然后在 Claude Code 中提出请求，例如：

> 在当前工作目录用 CronCreate 创建一个 `durable: true` 的一次性任务，约 5 分钟后在会话里回复“cron-up 验证成功”；完成后执行 `/exit` 退出会话

CronCreate 是 Claude Code 内部工具，不是在终端里直接执行的 shell 命令。推荐让无人值守任务在完成并保存结果后执行 `/exit`，但是否执行该指令仍取决于任务本身

### 3. 验证发现和预热

依次用 `cron-up list` 确认任务已被发现并查看时间，用 `cron-up run` 立即巡检一次，再用 `cron-up` 查看服务、会话和告警。需要查看后台界面时，运行 `cron-up logs <目录名或任务id>`；完整命令和日志选项见[日常使用](#日常使用)

定时巡检每 5 分钟一轮。周期任务在设定时间前 6 分钟进入预热窗口；所有一次性任务都统一再增加 90 秒前瞻，最早可在设定时间前 7.5 分钟进入窗口。实际启动由窗口内的巡检触发，具体时间取决于巡检相位，并不是固定提前 6 或 7.5 分钟

其中，落在 `:00` 或 `:30` 的一次性任务按当前上游规则还可能提前至多 90 秒投递

任务还没到预热窗口时，`cron-up run` 不会为它提前常驻一个会话；若已经有一轮巡检在运行，后到的一轮会跳过

## 日常使用

```bash
cron-up                        # 总览：服务、配置、最近任务、预热会话与告警
cron-up list                   # 列出所有工作区的任务时间、摘要、模型配置与预热状态
cron-up run                    # 立即手动巡检一次
cron-up logs                   # 查看最近 100 行巡检日志
cron-up logs team-space        # 按文件名片段选择后台会话日志
cron-up logs team-space--00000002 -f
```

会话日志按文件名片段匹配，可以输入目录名、任务 id 或两者组合；命中多个日志时会列出候选，请补充更长的片段

### 看懂总览和任务列表

总览优先看三处：

- **服务与上次巡检**：launchd 已加载不等于巡检仍在成功运行，心跳可以帮助识别启动链失效
- **最近**：按预计投递时间排序，而不是只按 cron 的设定时间排序
- **需要留意**：配置、启动链、会话登记、预热失败和失去扫描范围的会话等告警

下面是 `cron-up list` 的输出格式示例，日期、时间和 pid 以本机实际输出为准：

```text
共 1 个工作区、2 个定时任务

/Users/you/code/my-project
  10-24 19:52          一次性      52 19 24 10 *     验证 cron-up [预热中 12345]
  10-25 09:00 → 09:30  周期·永久   0 9 * * *         每日汇总
```

常见状态和标签：

| 显示 | 含义 |
| --- | --- |
| `设定时间 → 预计时间` | 前者是 cron 设定时间，后者是按已知上游规则估算的投递时间；没有偏差时只显示一个时间 |
| `启动中 <pid>` | 会话进程已启动，尚未在 Claude Code 会话登记中确认 |
| `预热中 <pid>` | 已确认后台会话登记且预热进程存活；归属是否已写回可结合巡检日志判断 |
| `待预热` | 已进入预热窗口，但当前还没有承接会话；结合总览告警判断原因 |
| `冷却中` / `失败N次` | 预热启动失败，正在退避或已经累计失败 |
| `终端接管` | 用户通过 `--resume` 接管了该会话，cron-up 不再另拉或结束它 |
| 标签为空 | 可能还没到预热窗口，也可能原创建者会话仍在线，需要结合时间列和总览判断 |
| `已错过` | 一次性任务的设定时间已经过去；有效 `createdAt` 是 cron-up 判断错过待补的必要字段 |
| `一年内无` | cron 可解析，但 366 天展示窗口内没有未来落点；二月三十日这类日历上永远不出现的表达式也归入此状态 |
| `cron 无效` | 表达式解析失败，或字段值域、区间导致合法值集合为空，巡检会跳过该任务 |

## 任务时间与执行

文档和命令输出中的时间均为 macOS 本机时间，cron-up 也用本地时区计算预热和展示。三个时间概念不要混用：

1. **设定时间**：cron 表达式对应的分钟
2. **预计投递时间**：计入已知上游抖动规则后的估算，可能早于或晚于设定时间
3. **实际执行时间**：Claude Code 会话实际收到并开始处理任务的时间，还受秒级轮询、会话状态和上游实现影响

周期任务通常在设定时间之后投递，每日任务使用原生随机 id 时经常接近固定的 30 分钟上限；一次性任务落在 `:00` 或 `:30` 时可能提前至多 90 秒。约 5 分钟周期且匹配特定表达式的上游任务还可能走提前 15 秒的分支，当前预测没有复刻该分支，完整规则和例外见[投递时间算法](docs/internals.md#投递时间算法)

因此，“设定时间到了但还没执行”不一定是故障，应先看 `cron-up list` 的预计时间和总览告警

电脑休眠期间，launchd 醒来后只补跑一轮巡检：

- 错过的周期任务不会补执行
- 错过的一次性任务通常会在后台会话启动时由 Claude Code 补执行；手写任务缺少有效 `createdAt` 时，cron-up 无法据此识别错过待补

## 会话生命周期与恢复

预热会话按任务需要创建，周期任务不依靠跨周期累积上下文。复用与回收只在巡检轮次中按启发式条件判断，不等于对任务完成状态做强保证：

- 周期任务的预热窗口从设定时间前 6 分钟开始，一次性任务最早从设定时间前 7.5 分钟开始；具体启动时间取决于窗口内的巡检相位
- 新会话启动后，当轮每 3 秒重扫一次登记，最多等待 24 秒；这只是加速归属写回，不是启动判死时限
- 进程超过 3 分钟仍未完成登记时，由后续巡检判定卡死并终止；因为巡检每 5 分钟一轮，实际处置时间不是精确的启动后第 3 分钟
- 没有成功登记的启动连续失败 3 次后，该任务暂停重试 30 分钟；按任务分别计数，成功登记会清零，已死亡条目的失败记录跨预热窗口保留并在 48 小时后老化
- 回收除了要求界面静默超过 3 分钟，还要求距该任务下次需要超过 7 分钟；同样只在巡检时判断
- 距下次需要不超过 7 分钟时会继续复用现有会话，例如每 5 分钟执行的任务通常无法满足回收余量，其会话可能长期在线，不能按“窗口外没有会话”估算内存
- 同分钟大量任务会同时拉起多个 Claude Code 会话，每个会话可能占用数百 MB，实际以本机为准；正常回收后不再保留这些预热会话的内存开销

后台会话与普通会话一样保存对话记录，可以在终端恢复：

```bash
claude --resume <sessionId>      # 或 claude -r 在列表中选择
```

对话记录位于 `~/.claude/projects/<目录编码>/<会话ID>.jsonl`。如果恢复后原后台进程已经退出、同一 sessionId 仍在终端运行，cron-up 会停止管理它，不结束终端进程；该终端会话关闭后，后续巡检可重新预热

## 自动维护的写入边界

同一轮中，同一批待处理的自动续期和归属改写会合并为带 mtime 乐观检测的原子写入；新会话在后续完成登记、需要补写归属时，可能另做一次原子写入。若检测到 Claude Code 同时更新了 `lastFiredAt`、删除了一次性任务或进行了其他修改，本轮对应写入会暂缓并在后续重试

这只是降低并发覆盖概率，不是与 Claude Code 共用的互斥锁。最后一次检查与原子替换之间仍存在极小竞态，详见[内部机制](docs/internals.md#任务文件维护与并发)

卸载 cron-up 不会撤销这些已经写入任务文件的修改

## 配置与产物

配置文件为 `~/.local/share/cron-up/config.json`，只有扫描范围一个字段：

```json
{ "roots": ["/Users/you/code", "/Users/you/work"] }
```

可以直接编辑 roots，通常最多等下一轮巡检生效；也可以运行：

```bash
cron-up install --roots "$HOME/code,$HOME/work"
```

重跑 install 会重写配置、启动脚本与 LaunchAgent，并移除旧版本遗留的废弃配置字段

巡检间隔、提前量、扫描深度、失败退避等均为固定行为，完整常量和生命周期规则见[内部机制](docs/internals.md#巡检与会话生命周期)

### 按工作区和任务指定模型

在工作区放置可选的 `.claude/cron-up.json`，可以指定该目录预热会话的默认模型，并按任务覆盖：

```json
{
  "model": "claude-opus-5-5",
  "tasks": {
    "00000002": {
      "model": "sonnet"
    }
  }
}
```

两个 `model` 都可省略，优先级为“任务 `model` > 工作区 `model` > 不传 `--model`，沿用 Claude Code 自身配置”。模型值由本机 Claude Code 解释，可以使用其支持的别名或完整模型名；cron-up 不维护模型清单，也不会提前验证模型是否可用，启动失败仍走原有的重试与冷却流程

`tasks` 的键使用 cron-up 的任务键：常规 CronCreate 任务就是 `.claude/scheduled_tasks.json` 中对应任务的 `id`；无 id 的手写任务使用 `anon:` 内容摘要键，这类任务更适合只配置工作区默认模型

该配置只作用于 **cron-up 新拉起的预热会话**：

- 修改配置不会自动重启或切换已有会话，等该任务下次重新预热时生效；`cron-up list` 显示的是当前配置值，不是运行中会话的实际模型探测结果
- 原创建者会话仍在线时，任务继续复用该会话及其模型，不另起具有指定模型的预热会话
- 配置文件存在但 JSON 损坏、顶层形状或模型字段类型不对时，巡检会告警，并暂停该工作区的新预热，避免悄悄回退到默认模型；已有会话仍照常管理，配置问题不计入启动失败次数

此文件由用户维护，install、uninstall 和 `--purge` 都不会创建、改写或删除它

| 产物 | 位置 |
| --- | --- |
| 命令行与代码 | npm 全局目录，具体位置取决于 Node 与 npm 安装方式 |
| 配置文件 | `~/.local/share/cron-up/config.json` |
| 工作区模型配置（可选） | `<工作区>/.claude/cron-up.json`，由用户维护 |
| 运行状态 | `~/.local/share/cron-up/state.json`，按工作区与任务 id 记录预热 |
| 巡检心跳 | `~/.local/share/cron-up/heartbeat`，每轮成功完成后写入 |
| LaunchAgent | `~/Library/LaunchAgents/local.cron-up.plist` |
| 启动脚本 | `~/.local/share/cron-up/cron-up-service` |
| 巡检日志 | `~/Library/Logs/cron-up/launchd.{out,err}.log` |
| 各任务会话日志 | `~/Library/Logs/cron-up/sessions/<工作区折名>--<任务id>.log`，轮转保留一代 `.1` |
| Claude Code 对话记录 | `~/.claude/projects/<目录编码>/<会话ID>.jsonl`，由 Claude Code 管理 |

会话日志可能包含任务输出，文件权限为 0600、目录权限为 0700。日志文件名中的工作区折名由完整工作区路径生成，日常使用建议通过 `cron-up logs` 查找，不要手工猜文件名

cron-up 自身的巡检和会话管理不主动访问 npm registry 或其他网络服务；安装和升级时由 npm 访问 registry。被启动的 Claude Code 会话仍可能联网，cron-up 不对其网络活动作限制

### 配置无法解读时

不带 roots 重跑 install 时，只有可读取且 roots 类型有效的现有配置才会被沿用；配置无法解读时会提示并回退到默认范围 `~/space`、`~/workspace`、`~/tasks`，随后立即尝试首轮巡检，可能续期或改写其中的任务文件

修复时可以直接改正上述配置文件；需要通过 install 重建且不想使用默认范围时，必须显式传入完整的 `--roots`

## 升级与启动链维护

升级 cron-up：

```bash
npm i -g cron-up@latest --prefer-online
cron-up install
cron-up
```

最后一步确认首行版本、launchd 状态、上次退出码和“需要留意”。刚发布新版本时 registry 与本机缓存可能有延迟，维护者发版后的逐机升级使用显式版本号，见[发布后的逐机升级与验收](docs/release.md#每次发版后的逐机升级与验收)

launchd 的初始 PATH 很小，因此 install 会把 `node` 与 `cron-up` 所在 bin 目录写入 `~/.local/share/cron-up/cron-up-service`。预热中的 `claude` 则由 `/bin/zsh -lic` 启动，依赖登录交互 shell 的配置，而不是仅靠前述两个目录

出现以下情况后应重跑 `cron-up install`：

- 切换、删除或更换 Node 安装方式
- 修改 roots 或需要重建 LaunchAgent
- 总览提示启动脚本失效、PATH 找不到 node／cron-up，或巡检心跳沉默

若 `zsh -lic 'command -v claude'` 失败，先修复交互 zsh 中的 `claude` 命令及其环境，再重跑 install。手动 `cron-up run` 成功而 launchd 失败时，也应优先比较这两种环境的差异

## 卸载与数据保留

`cron-up uninstall` 管理的是本机服务和 cron-up 自有产物，不等于删除所有相关数据：

| 操作或数据 | `cron-up uninstall` | `cron-up uninstall --purge` |
| --- | --- | --- |
| 停止仍可安全跟踪的预热会话 | 是 | 是 |
| 移除 LaunchAgent 和 plist | 是 | 是 |
| 删除 `~/.local/share/cron-up` 中的配置、状态、心跳和启动脚本 | 否 | 是 |
| 删除 `~/Library/Logs/cron-up` 中的巡检与会话日志 | 否 | 是 |
| 卸载 npm 全局 `cron-up` 命令 | 否 | 否 |
| 删除 Claude Code 任务或 `~/.claude/projects` 对话记录 | 否 | 否 |
| 删除各工作区的 `.claude/cron-up.json` | 否 | 否 |
| 恢复任务文件中的 `permanent`、`createdBy*` 字段 | 否 | 否 |

完全移除命令行和 cron-up 自有产物：

```bash
cron-up uninstall --purge
npm uninstall -g cron-up
```

Claude Code 任务和对话记录需要在 Claude Code 侧另行处理。卸载后任务文件仍然存在，但 cron-up 不再提供预热、续期或会话回收；不要把这个状态理解为任务字段已经恢复原状

## 故障排查

| 现象 | 排查方法 |
| --- | --- |
| 总览提示“冷却中” | 运行 `cron-up logs <目录名>--<任务id>` 查看启动界面；常见原因是目录信任、工具授权、登录状态或 shell 环境，冷却结束不代表问题已经修复 |
| 设定时间到了但没有执行 | 先看 `cron-up list` 的预计投递时间，排除上游抖动；再看总览告警和对应会话日志，并确认当时电脑没有休眠 |
| 总览提示“启动脚本已失效 / PATH 找不到 node” | 按[升级与启动链维护](#升级与启动链维护)检查并重跑 `cron-up install` |
| 总览提示“巡检已沉默” | 先运行 `cron-up logs` 查看巡检和 stderr 提示，再检查启动链并重跑 install |
| `last exit code=2` | 通常是配置损坏或 roots 类型不对；直接修复 `~/.local/share/cron-up/config.json`，或按[配置无法解读时](#配置无法解读时)的说明显式传入完整 roots 重跑 install |
| 手动 `cron-up run` 正常、定时执行不正常 | 比较终端与 launchd／`zsh -lic` 的 PATH、Node 和 `claude` 环境；换过 Node 安装方式后重跑 install |
| 任务表显示“已错过” | 对一次性任务检查后台会话是否启动及其日志；手写任务缺少有效 `createdAt` 时，cron-up 不会按错过待补处理 |
| 日志里出现“卡死” | 表示超过登记宽限后由巡检终止，常见于人工作答界面，也可能是会话登记或启动形态变化；先看会话日志和总览的登记格式告警 |
| 从旧版升级后仍有目录级预热 | 查看[旧版迁移](docs/migration.md)，核实是否因缺少进程指纹而需要人工处理 |

## 已知限制

- 仅支持 macOS，且依赖未公开的 Claude Code 内部实现；上游升级可能改变任务归属、登记格式、进程结构和投递算法
- 电脑休眠期间错过的周期任务不会补执行；一次性任务的补执行依赖上游机制和必要任务字段
- 每个进入窗口且原归属不在场的任务对应一个会话，同分钟大量任务可能带来明显内存压力
- 手写或第三方生成的任务文件不是推荐入口；任务应有唯一 id、显式 `recurring` 和符合上游语义的字段，一次性任务还需要毫秒时间戳 `createdAt` 才能由 cron-up 判断错过待补
- 工作区的任务文件被整体删除或目录移出 roots 后，仍在运行的预热可能不再被回收；总览会列出能识别的此类会话，需要人工处理
- mtime 乐观检测不能完全关闭跨进程写入竞态；需要绝对写入保证时，应由上游提供共享锁或公开写接口
- 即使预热和投递正常，任务仍可能因模型、工具、权限、网络或 prompt 本身而失败
